# Nimbus API rate limits

API responses include rate-limit information. When a client receives HTTP 429, honor the `Retry-After` value and use exponential backoff with jitter. Avoid retrying non-idempotent requests blindly, because a timeout does not prove that the server did not accept a write.

## Safe retry steps

1. Record the endpoint, method, status code, request ID, and timestamp.
2. Pause for the `Retry-After` duration, or use capped exponential backoff when it is absent.
3. Retry reads normally; retry writes only when the operation is documented as idempotent and uses the same idempotency key.
4. Reduce concurrency and batch size if 429 responses continue.

## Escalation evidence

If limits are reached consistently, provide the endpoint, request volume, response headers, and timestamps without sharing credentials. A request ID helps support trace the decision without exposing payload secrets.
